# textchisel: Comprehensive Technical Reference Guide

**An implementation-ready reference for building an inverse-kinematics-inspired prompt space navigator with quality dimension sliders, LLM-as-judge evaluation, and a hidden grammar layer for prompt modification.**

---

## TOP 5 CRITICAL REFERENCES (Extra Implementation Detail)

Before diving into per-area references, these five resources are the most architecturally significant for textchisel and deserve priority attention.

### 🔑 Critical Reference 1: LLM-Rubric (Hashemi et al., ACL 2024)
- **Source:** https://aclanthology.org/2024.acl-long.745/ | https://github.com/microsoft/LLM-Rubric
- **Why #1:** This is the single most architecturally aligned paper. It evaluates across **9 dimensions simultaneously**, uses a **calibration network** to combine per-dimension LLM scores, and explicitly handles the problem of different judges weighting dimensions differently — directly parallel to textchisel's slider concept.
- **Architecture to adopt:** (1) 9 rubric questions (Q1–Q9) each assessing a different dimension, plus Q0 for overall quality. (2) A small feed-forward neural network takes LLM's probability distributions across all rubric questions and predicts calibrated human-aligned scores. Includes judge-specific parameters (modeling individual biases) and judge-independent parameters (shared logic). Trained with L2 loss. (3) Synthetic data augmentation: 750 synthetic dialogues generated by 5 different LLM approaches with varying quality levels.
- **Direct slider mapping:** Dimension sliders map to weight parameters in the calibration network — adjusting how much each dimension contributes to overall score. Raw LLM scores achieve **2× worse RMS error** than calibrated scores.
- **Priority:** **MVP** — the calibration layer is essential from day one.

### 🔑 Critical Reference 2: CriSPO (He et al., Amazon Science, AAAI 2025)
- **Source:** https://arxiv.org/abs/2410.02748 | https://github.com/amazon-science/CriSPO
- **Why #2:** CriSPO's multi-aspect critique-suggestion mechanism is essentially what textchisel's grammar layer needs. It automatically discovers quality aspects (word count, style, precision, formality), generates per-aspect critiques, and provides actionable suggestions for prompt modification.
- **Architecture to adopt:** Two-component system: (1) **Multi-aspect Critique-Suggestion Meta-prompt (Mc)** that compares generated vs. reference text across aspects, producing per-aspect critiques AND suggestions. (2) **Receptive Optimizer Meta-prompt (Mo)** that takes critiques+suggestions + optimization trajectory → generates improved prompt in CoT manner. Also includes **Automatic Suffix Tuning (AST)** that divides prompts into chunks, each optimizing a different metric — directly applicable to multi-slider optimization.
- **Key adaptation:** Instead of discovering aspects, textchisel's sliders define the aspects. Feed user-defined quality dimensions as the aspects for critique-suggestion generation.
- **Priority:** **MVP** — core grammar layer engine.

### 🔑 Critical Reference 3: Concept Sliders (Gandikota et al., ECCV 2024)
- **Source:** https://sliders.baulab.info/ | https://arxiv.org/abs/2311.12092 | https://github.com/rohitgandikota/sliders
- **Why #3:** While designed for diffusion models, Concept Sliders establishes the mathematical framework for composable, disentangled attribute control via low-rank adapters — the exact paradigm textchisel needs for independent quality dimension control.
- **Architecture to adopt:** Each slider is a LoRA adapter (rank 4) trained to represent a single concept direction. **Disentanglement via preservation sets**: to edit "age" without affecting "race," specify preservation concepts; optimization forces the slider to work identically across all preservation concepts. **Composability**: Multiple sliders compose linearly in weight space: θ* = θ + Σ_i α_i ΔW_i. Because LoRA updates are low-rank, they occupy approximately orthogonal subspaces, enabling near-independent composition of **50+ simultaneous sliders**.
- **For textchisel:** Adapt the contrastive pair approach: "high formality prompt" vs "low formality prompt" to find the formality direction in prompt/embedding space. Train one LoRA per quality dimension with preservation sets preventing interference.
- **Priority:** **Phase 2** — advanced disentanglement after rule-based MVP.

### 🔑 Critical Reference 4: TextGrad (Yuksekgonul et al., Nature 2025)
- **Source:** https://github.com/zou-group/textgrad | https://arxiv.org/abs/2406.07496
- **Why #4:** Provides a production-ready PyTorch-like API for text optimization. Its `Variable`, `TextLoss`, and `TGD` (Textual Gradient Descent) abstractions map naturally to textchisel's architecture — each quality slider = a `TextLoss` with a natural language evaluation instruction.
- **Architecture to adopt:**
  ```python
  answer = tg.Variable(prompt_text, requires_grad=True, role_description="prompt to optimize")
  loss_fn = tg.TextLoss("Evaluate the urgency and actionability of this prompt.")
  optimizer = tg.TGD(parameters=[answer])
  loss = loss_fn(answer)
  loss.backward()  # Generates textual gradients (natural language critique)
  optimizer.step()  # Applies gradient-directed edits
  ```
- **Key feature:** `requires_grad=True/False` marks which prompt parts are optimizable vs. fixed — perfect for textchisel's locked/unlocked dimension distinction.
- **Priority:** **MVP** — backbone optimization engine.

### 🔑 Critical Reference 5: pymoo's R-NSGA-III with Repair Operators
- **Source:** https://pymoo.org/ | https://github.com/anyoptimization/pymoo
- **Why #5:** Production-ready Python multi-objective optimization. R-NSGA-III directly maps user slider positions to reference points, and the Repair operator pattern is the cleanest way to implement dimension locking.
- **Architecture to adopt:**
  ```python
  from pymoo.algorithms.moo.rnsga3 import RNSGA3
  ref_points = np.array([[0.8, 0.3, 0.9]])  # User slider positions as targets
  algorithm = RNSGA3(ref_points=ref_points, pop_per_ref_point=50, mu=0.1)
  
  class DimensionLockRepair(Repair):
      def _do(self, problem, X, **kwargs):
          for dim_idx, locked_val in locked_dims.items():
              X[:, dim_idx] = locked_val
          return X
  ```
- **Priority:** **MVP** — core optimization engine.

## AREA 1: LLM-as-Judge Evaluation Systems

### G-Eval (Liu et al., EMNLP 2023)
- **Source:** https://arxiv.org/abs/2303.16634 | https://aclanthology.org/2023.emnlp-main.153/
- **Relevance to textchisel:** Foundational algorithm for the core evaluation loop — taking a quality dimension description (e.g., "urgency"), auto-generating evaluation steps via CoT, and scoring via probability-weighted form-filling.
- **Technical Enablers:** Three-component pipeline: (1) Task Introduction + Evaluation Criteria → (2) Auto-generated Chain-of-Thought Evaluation Steps → (3) Form-filling scoring. **Probability-weighted scoring**: extracts probability distribution over score tokens; final score = Σ(p(score_i) × score_i), producing continuous scores (e.g., 3.7) that reduce ties and improve Spearman correlation to **0.514** (summarization).
- **Implementation Lessons:** LLM self-bias consistently scores LLM-generated text higher than human text. Log-probs are not available on all API models — plan a fallback to multi-sample averaging. CoT evaluation steps should be generated once per dimension and cached.
- **Priority for MVP vs. Later:** **MVP** — core scoring algorithm.

### DeepEval's G-Eval Implementation
- **Source:** https://github.com/confident-ai/deepeval | https://deepeval.com/docs/metrics-llm-evals
- **Relevance to textchisel:** Most mature open-source G-Eval implementation with exact code patterns for step generation and scoring. 13.6K GitHub stars.
- **Technical Enablers:** Two-phase algorithm: (1) Auto-generate evaluation steps from criteria string if not provided. (2) Score via form-filling with generated steps. Key constructor: `GEval(criteria="urgency", evaluation_params=[INPUT, ACTUAL_OUTPUT], model="gpt-4.1")`. Falls back gracefully when log-probs unavailable. Normalizes all scores to 0–1.
- **Implementation Lessons:** Pre-compute `evaluation_steps` for slider dimensions to improve consistency across runs. JSON parsing failures occur with weaker models — use structured output modes or retry logic.
- **Priority for MVP vs. Later:** **MVP** — reusable code.

### Prometheus / Prometheus-2 (Kim et al., ICLR 2024)
- **Source:** https://arxiv.org/abs/2310.08491 | https://github.com/prometheus-eval/prometheus-eval | https://huggingface.co/prometheus-eval/prometheus-7b-v2.0
- **Relevance to textchisel:** Demonstrates that open-source fine-tuned models can match GPT-4 as evaluators when given proper rubrics. Defines the **exact rubric format** for custom scoring.
- **Technical Enablers:** Rubric format directly reusable:
  ```
  ###Score Rubrics: [{criteria_description}]
  Score 1: {score1_description}
  Score 2: {score2_description}
  ...
  Score 5: {score5_description}
  ```
  Output: `Feedback: (detailed feedback) [RESULT] (score 1-5)`. Prometheus-2 uses weight merging of separately trained direct-assessment and pairwise-ranking models. Pearson correlation with humans: **0.897** vs GPT-4's **0.882**.
- **Implementation Lessons:** Reference answers alongside rubrics dramatically improve scoring quality. Cross-evaluation study shows fine-tuned judges perform badly on schemes they weren't trained for — choose evaluation format upfront.
- **Priority for MVP vs. Later:** **Phase 2** — cost optimization via open-source judge.

### MT-Bench Evaluation Methodology (Zheng et al., NeurIPS 2023)
- **Source:** https://arxiv.org/abs/2306.05685 | https://github.com/lm-sys/FastChat/tree/main/fastchat/llm_judge
- **Relevance to textchisel:** Established the LLM-as-judge paradigm, identified critical biases, and proposed mitigations essential for reliability.
- **Technical Enablers:** Three evaluation paradigms (pairwise, single-answer grading, reference-guided). Bias mitigations: position bias (swap and compare), verbosity bias, self-enhancement bias. **Single-answer grading is nearly as effective as pairwise** with better scalability — validates textchisel's approach.
- **Implementation Lessons:** GPT-4 achieves >80% agreement with human judges — same as inter-human agreement. The default grading prompt instructs "Avoid any position bias" and "Begin your evaluation by providing a short explanation."
- **Priority for MVP vs. Later:** **MVP** — bias mitigation strategies.

### JudgeLM (Zhu et al., ICLR 2025)
- **Source:** https://arxiv.org/abs/2310.17631 | https://github.com/baaivision/JudgeLM
- **Relevance to textchisel:** Bias mitigation techniques directly applicable — swap augmentation, reference support, reference drop.
- **Technical Enablers:** Swap augmentation during training improves consistency by 5.44%. JudgeLM-33B outperforms its GPT-4 teacher (75.18% vs 66.47% agreement). **133.3× speedup** over sequential evaluation.
- **Implementation Lessons:** Fine-tuned judges are susceptible to adversarial inputs and superficial quality features.
- **Priority for MVP vs. Later:** **Phase 2** — self-hosted judge optimization.

### Calibration Techniques (Aggregated)
- **Source:** Multiple — LLM-Rubric calibration network, OpenRubrics voting@5, CalibraEval, Rulers framework (https://arxiv.org/html/2601.08654)
- **Relevance to textchisel:** Raw LLM scores have poor human alignment. Calibration is essential.
- **Technical Enablers:** (1) **Multi-sample averaging**: 3-5 scoring passes with slight temperature variation, aggregate via mean. (2) **Position switching**: run pairwise evals twice with swapped positions. (3) **Calibration network**: small NN mapping LLM distributions to human-aligned scores (2× RMSE improvement). (4) **Cross-family ensemble**: use diverse model families to reduce familial bias. (5) **Gold-set calibration**: 30-50 human-labeled examples for prompt iteration.
- **Implementation Lessons:** Voting@5 significantly outperforms single-pass. Cross-family ensembles reduce bias clustering.
- **Priority for MVP vs. Later:** Multi-sample averaging for **MVP**; calibration network for **Phase 2**.

### Automated Rubric Generation (OpenRubrics + FLASK)
- **Source:** OpenRubrics — https://arxiv.org/abs/2510.07743 | FLASK — https://arxiv.org/abs/2307.10928 | https://github.com/kaistAI/FLASK
- **Relevance to textchisel:** How to auto-generate scoring rubrics from natural language dimension descriptions.
- **Technical Enablers:** **OpenRubrics' Contrastive Rubric Generation (CRG)**: given prompt + preferred/rejected response, LLM generates discriminative criteria by contrasting what makes one better. Preference-label consistency filtering discards noisy rubrics. **FLASK**: 12 fine-grained skills with instance-specific rubric generation (different prompts require different skill subsets). Rubric-RM with voting@5 surpasses baselines by +6.8%.
- **Implementation Lessons:** FLASK's instance-wise skill annotation maps to textchisel where users select relevant dimensions per use case. Reduced position bias with rubric-based evaluation.
- **Priority for MVP vs. Later:** **MVP** for basic rubric generation; **Phase 2** for CRG.

## AREA 2: Automatic Prompt Optimization Techniques

### DSPy Framework (Stanford NLP)
- **Source:** https://github.com/stanfordnlp/dspy | https://dspy.ai/ | https://arxiv.org/abs/2310.03714
- **Relevance to textchisel:** DSPy's signature→prompt compilation is the closest existing architecture to the grammar layer. MIPROv2 optimizer demonstrates production-grade prompt modification.
- **Technical Enablers:** Signatures (`"question -> answer"`) compiled into full prompt templates. MIPROv2: (1) bootstrapping traces, (2) grounded instruction proposal, (3) Bayesian optimization via Optuna over (instructions × demos). Key constants: `AUTO_RUN_SETTINGS = {"light": {"n": 6}, "medium": {"n": 12}, "heavy": {"n": 18}}`. Cost: ~$2/run, ~20 min.
- **Implementation Lessons:** Per-predictor optimization creates large search spaces (10 candidates × 2 modules × 2 variables = 40 variables). Optimizers are composable: chain MIPROv2 → BootstrapFinetune.
- **Priority for MVP vs. Later:** **MVP** — signature/template system; **Phase 2** — full MIPROv2 optimization.

### ProTeGi / APO (Pryzant et al., EMNLP 2023)
- **Source:** https://aclanthology.org/2023.emnlp-main.494/ | arXiv:2305.03495
- **Relevance to textchisel:** The "textual gradient" concept maps directly to slider-driven prompt modification — each quality dimension slider generates a targeted gradient describing how to modify the prompt.
- **Technical Enablers:** (1) Given error examples, LLM generates a "gradient" (natural language summary of flaws). (2) Second LLM call edits prompt in "opposite semantic direction." (3) Monte Carlo sampling generates paraphrased variants. (4) Beam search + multi-armed bandit selects best candidates. Up to 31% improvement.
- **Implementation Lessons:** Textual gradients can be repetitive and struggle to align improvements with downstream behavior. CriSPO's decoupled critique-edit addresses this.
- **Priority for MVP vs. Later:** **MVP** — textual gradient concept.

### OPRO (Yang et al., Google DeepMind, ICLR 2024)
- **Source:** https://arxiv.org/abs/2309.03409 | https://github.com/google-deepmind/opro
- **Relevance to textchisel:** Simplest and most elegant approach — meta-prompt shows past prompts + scores, LLM generates improvements. Easily adapted per quality dimension.
- **Technical Enablers:** Meta-prompt with 4 sections: (1) meta-instructions, (2) top-20 historical instruction-score pairs, (3) task examples, (4) generation instruction. Loop: generate 8 candidates → evaluate on 3.5% sample → add to trajectory → keep top-20. Discovered "Take a deep breath and work step-by-step" naturally.
- **Implementation Lessons:** Requires larger LLMs as optimizers (GPT-4, PaLM 2-L). Semantically similar prompts can yield vastly different scores — landscape is noisy.
- **Priority for MVP vs. Later:** **Phase 2** — per-dimension trajectory management.

### EvoPrompt (Guo et al., ICLR 2024)
- **Source:** https://arxiv.org/abs/2309.08532 | https://github.com/beeevita/EvoPrompt
- **Relevance to textchisel:** Evolutionary operators for exploring prompt space when sliders create large combinatorial spaces.
- **Technical Enablers:** GA (roulette selection → crossover → mutation) and DE (mutate only differing parts, preserve shared). LLM performs crossover/mutation via structured prompts. Population initialization: human-written + LLM-generated.
- **Implementation Lessons:** DE's "preserve shared, mutate different" is directly applicable to maintaining base prompt while modifying quality-specific components. GA converges faster; DE reaches higher ceilings.
- **Priority for MVP vs. Later:** **Phase 3** — evolutionary exploration.

### PromptBreeder (Fernando et al., DeepMind, ICML 2024)
- **Source:** https://arxiv.org/abs/2309.16797
- **Relevance to textchisel:** Self-referential mutation where modification strategies themselves evolve — grammar layer rules can self-improve.
- **Technical Enablers:** Three-level hierarchy: task-prompts (P), mutation-prompts (M), hyper-mutation prompts (H). Five mutation operator classes. Lamarckian mutation generates prompts from correct examples.
- **Implementation Lessons:** Simple prompt "SOLUTION:" achieved 83.9% on GSM8K, surpassing OPRO's complex prompt. Don't over-constrain.
- **Priority for MVP vs. Later:** **Phase 3** — self-improving grammar layer.

### AdalFlow (SylphAI-Inc)
- **Source:** https://github.com/SylphAI-Inc/AdalFlow | arXiv:2501.16673
- **Relevance to textchisel:** Most production-ready PyTorch-like framework unifying textual gradients, few-shot bootstrap, and instruction history. Handles multi-component pipelines.
- **Technical Enablers:** `Component` ↔ `nn.Module`, `Parameter(type=PROMPT)` for text optimization, `Parameter(type=DEMOS)` for few-shot. LLM-AutoDiff: forward pass forms computation graph → backward engine generates feedback → optimizer proposes new prompts. Jinja2 templates.
- **Implementation Lessons:** Time-sequential feedback matters — ignoring sub-query order leads to suboptimal updates.
- **Priority for MVP vs. Later:** **Phase 2** — unified optimization framework.

## AREA 3: Multi-Objective Optimization with Human-in-the-Loop

### MOPO: Multi-Objective Prompt Optimization (COLING 2025)
- **Source:** https://aclanthology.org/2025.coling-main.375/ | https://github.com/YarikMR/MOPO
- **Relevance to textchisel:** Directly optimizes prompts across multiple quality objectives using NSGA-II. Outputs a Pareto set of prompts with different weightings.
- **Technical Enablers:** Three-layer prompt architecture. NSGA-II with genetic operations (crossover = combining prompts, mutation = paraphrasing). Up to 15pp improvement across all objectives with only 1-2pp loss per single objective.
- **Implementation Lessons:** Combining operations (crossover) yield more impact than paraphrasing alone. LLM-as-mutator can generate near-copies; diversity maintenance is critical.
- **Priority for MVP vs. Later:** **MVP** — validates multi-objective prompt optimization is viable.

### pymoo Library (NSGA-II/III)
- **Source:** https://pymoo.org/ | https://github.com/anyoptimization/pymoo
- **Relevance to textchisel:** Production-ready multi-objective optimization. R-NSGA-III directly maps slider positions to reference points.
- **Technical Enablers:** NSGA-II for 2-3 objectives, NSGA-III for 4+. R-NSGA-III takes user-specified reference points. Repair operators for dimension locking (force locked values after each generation). Pseudo-weights for MCDM, built-in visualization.
- **Implementation Lessons:** Equality constraints are challenging for evolutionary algorithms — use Repair operators or bound clamping (`xl=xu=locked_value`) instead. Set `xl[i] = xu[i] = locked_value` as simplest approach.
- **Priority for MVP vs. Later:** **MVP** — core optimization engine.

### Null-Space Optimization from Robotics IK
- **Source:** https://www.nature.com/articles/s41598-024-81174-8 | Siciliano & Khatib, Springer Handbook of Robotics
- **Relevance to textchisel:** The exact mathematical framework for the governing analogy. When user locks quality dimensions (end-effector position), the system optimizes remaining dimensions in the null space of locked constraints.
- **Technical Enablers:** Forward kinematics: `x = f(θ)`. Jacobian: `J = ∂x/∂θ`. Pseudoinverse solution: `θ̇ = J†ẋ + (I - J†J)θ̇_N` where N = null-space projector. Gradient Projection: `θ̇ = J†ẋ_desired + α·N·∇H(θ)` where H is secondary objective. Damped Least Squares avoids singularities: `J† = Jᵀ(JJᵀ + λ²I)⁻¹`.
- **Implementation Lessons:** Jacobian must be estimated numerically or via surrogate model. Near singularities, pseudoinverse produces huge velocities — damping essential. QP formulation more robust than pseudoinverse for joint limits.
- **Priority for MVP vs. Later:** **Phase 2** — mathematical framework after rule-based MVP.

### BoTorch Multi-Objective Bayesian Optimization
- **Source:** https://botorch.org/docs/multi_objective/ | BOPE tutorial: https://botorch.org/docs/tutorials/bope/
- **Relevance to textchisel:** State-of-the-art BO with Expected Hypervolume Improvement (EHVI). BOPE learns user preferences from pairwise comparisons.
- **Technical Enablers:** qLogNEHVI for noisy evaluations (LLM outputs). Reference point specification required. BOPE alternates preference exploration (PairwiseGP + EUBO-ζ) with experimentation. GPU-accelerated via PyTorch.
- **Implementation Lessons:** EHVI computation scales poorly beyond ~5 objectives — use approximate box decompositions. BOPE avoids needing explicit utility functions.
- **Priority for MVP vs. Later:** **Phase 2** — surrogate-based optimization.

### Pareto Navigator Method
- **Source:** Eskelinen et al., OR Spectrum 32, 211-227 (2010) | Hartikainen et al., EJOR 275(1), 238-251 (2019)
- **Relevance to textchisel:** Interactive navigation on polyhedral approximation of Pareto front. Two-step framework: offline computation + online navigation.
- **Technical Enablers:** Achievement scalarizing functions for navigation. Slider UI with selector (handle), lower restrictor, upper restrictor per objective. Discounting mechanism limits how rapidly solutions change — prevents jarring jumps on slider drag.
- **Implementation Lessons:** Offline-online split essential: precompute Pareto approximation, then navigate in real-time. Discounting prevents jarring jumps.
- **Priority for MVP vs. Later:** **Phase 2** — navigation UX refinement.

### Interactive Decision Maps (Lotov et al.)
- **Source:** Lotov, Bushenkov & Kamenev, Kluwer Academic Publishers, 2004 | https://en.wikipedia.org/wiki/Interactive_Decision_Maps
- **Relevance to textchisel:** Displays 2D slices of higher-dimensional Pareto fronts with scroll-bars controlling other objectives — directly maps to the slider UI.
- **Technical Enablers:** Edgeworth-Pareto Hull computation. Bi-objective slices that monotonically extend/shrink as other objectives' constraints change. Animation by scrolling through constraint values.
- **Implementation Lessons:** Each scroll-bar = one quality dimension slider; 2D plot shows trade-off between selected dimensions.
- **Priority for MVP vs. Later:** **Phase 3** — advanced visualization.

### Optuna Human-in-the-Loop
- **Source:** https://optuna.readthedocs.io/en/stable/tutorial/20_recipes/009_ask_and_tell.html | https://optuna-dashboard.readthedocs.io/en/latest/tutorials/hitl.html
- **Relevance to textchisel:** Production-ready ask-and-tell interface with web dashboard for interactive optimization.
- **Technical Enablers:** `study.ask()` gets parameters, `study.tell(trial, values)` reports results. Multi-objective + constrained optimization support. ChoiceWidget for human evaluation. Artifact store for generated content.
- **Implementation Lessons:** `constant_liar=True` prevents duplicate suggestions during parallel evaluation. Only GP-based BO supports HITL optimization mode.
- **Priority for MVP vs. Later:** **Phase 2** — structured optimization loop.

## AREA 4: Controllable Text Generation

### Concept Sliders (Gandikota et al., ECCV 2024)
- **Source:** https://sliders.baulab.info/ | https://arxiv.org/abs/2311.12092 | https://github.com/rohitgandikota/sliders
- **Relevance to textchisel:** Defines the composable slider paradigm with disentanglement and linear composition.
- **Technical Enablers:** LoRA rank-4 adapters per concept. Composition: θ* = θ + Σ_i α_i ΔW_i. Disentanglement via preservation sets. 50+ sliders compose without degradation.
- **Implementation Lessons:** Low-rank constraint essential for precision AND efficiency. Training requires only 4-6 pairs.
- **Priority for MVP vs. Later:** **Phase 2** — adapt for text domain.

### SliderSpace (Gandikota et al., ICCV 2025)
- **Source:** https://sliderspace.baulab.info/ | https://arxiv.org/abs/2502.01639 | https://github.com/rohitgandikota/sliderspace
- **Relevance to textchisel:** Automatically discovers meaningful control dimensions via PCA on CLIP features.
- **Technical Enablers:** (1) Generate samples, (2) extract CLIP embeddings, (3) PCA on embedding space, (4) train LoRA per PC direction. 10 PCA directions match diversity of 64 manual sliders.
- **Implementation Lessons:** PCA on semantic embeddings provides automatic, interpretable decomposition. Trains 4× faster than manual Concept Sliders.
- **Priority for MVP vs. Later:** **Phase 3** — automatic dimension discovery.

### PPLM — Plug and Play Language Models (ICLR 2020)
- **Source:** https://arxiv.org/abs/1912.02164 | https://github.com/uber-research/PPLM
- **Relevance to textchisel:** Inference-time steering without retraining. Adjustable `stepsize` = slider position.
- **Technical Enablers:** Forward-backward-forward loop: compute gradients from attribute model, perturb hidden states H_t += α·∇H. Two attribute models: Bag-of-Words (word lists) and discriminator (single learned layer). KL penalty prevents degeneration.
- **Implementation Lessons:** ~10× slower than standard generation. Repetition/degeneration is main failure mode. Multi-attribute composition: sum gradients from multiple models — works but can conflict.
- **Priority for MVP vs. Later:** **Phase 3** — only if self-hosting models.

### Classifier-Free Guidance for Text (Sanchez et al., 2023)
- **Source:** https://arxiv.org/abs/2306.17806
- **Relevance to textchisel:** Zero-training, lightweight inference-time technique where γ (guidance scale) acts as slider control.
- **Technical Enablers:** `log P̂ = log P(unconditional) + γ(log P(conditional) − log P(unconditional))`. **Already integrated into HuggingFace Transformers** as `UnbatchedClassifierFreeGuidanceLogitsProcessor`. `guidance_scale` and `negative_prompt_ids` parameters. Equivalent to 2× parameter count improvement.
- **Implementation Lessons:** Double computation cost. γ ∈ [1.2, 2.0] is sweet spot; >3 causes artifacts.
- **Priority for MVP vs. Later:** **Phase 2** — zero-cost slider mechanism for self-hosted models.

### Activation Steering / Representation Engineering (Zou et al., 2023)
- **Source:** https://arxiv.org/abs/2310.01405 | https://github.com/steering-vectors/steering-vectors
- **Relevance to textchisel:** Most promising approach for continuous, independent multi-attribute control via steering vectors in activation space.
- **Technical Enablers:** Extract steering vector: mean activation difference between contrastive pairs. Apply at inference: a_l' = a_l + α·v_C. Demonstrated on truthfulness (+30% TruthfulQA), personality traits, formality, reasoning. Library: `SteeringVector.train(model, tokenizer, contrastive_pairs)` → `sv.apply(model, layer=15, multiplier=1.5)`.
- **Implementation Lessons:** Multi-vector steering causes interference. Mitigations: apply at different layers, orthogonalize vectors, use vector rejection. Mid-layers (13-18 for 32-layer models) work best.
- **Priority for MVP vs. Later:** **Phase 3** — advanced attribute control.

### DExperts (Liu et al., ACL 2021)
- **Source:** https://arxiv.org/abs/2105.03023 | https://github.com/alisawuffles/DExperts
- **Relevance to textchisel:** Most practical production approach for multi-attribute control. Train small expert/anti-expert per dimension.
- **Technical Enablers:** Product of experts: `logit = log P_base + α(log P_expert − log P_anti-expert)`. α = slider value. Experts much smaller than base model. Operates on logits only — faster than PPLM.
- **Implementation Lessons:** Multi-attribute: multiple expert/anti-expert pairs combined additively. Requires training per attribute but experts are small.
- **Priority for MVP vs. Later:** **Phase 2** — self-hosted production control.

## AREA 5: Spider Chart / Radar Chart UI

### Nadieh Bremer's D3 Radar Chart
- **Source:** https://www.visualcinnamon.com/2015/10/different-look-d3-radar-chart/ | https://gist.github.com/nbremer/21746a9668ffdf6d8242
- **Relevance to textchisel:** Gold-standard D3 radar chart with multi-polygon overlay, hover highlight, glow effects.
- **Technical Enablers:** Configurable `RadarChart()` function. SVG paths for filled polygons. Cardinal-closed interpolation for `roundStrokes`. Hover dims all other polygons (opacity → 0.1).
- **Implementation Lessons:** Use as base rendering engine. Needs extension for drag behavior on vertex circles.
- **Priority for MVP vs. Later:** **MVP** — core visualization.

### D3 Draggable Radar Charts
- **Source:** https://github.com/azole/d3-radar-chart-draggable | https://github.com/tenji240/d3-radar-chart (with per-axis min/max ranges)
- **Relevance to textchisel:** Directly implements draggable nodes on D3 radar. tenji240's version adds per-axis min/max bounds.

## AREA 6: Prompt Structure and Grammar Layer Architecture

### The Prompt Report (Schulhoff et al., 2024)
- **Source:** https://arxiv.org/abs/2406.06608 | https://trigaten.github.io/Prompt_Survey_Site/
- **Relevance to textchisel:** The raw ingredient list for the grammar layer — 58 techniques organized into 6 categories.
- **Technical Enablers:** 6 atomic prompt components: Directive, Examples, Output Formatting, Style Instructions, Role, Additional Information — each independently parameterizable. 33 vocabulary terms with formal definitions. Zero-shot techniques map to quality dimensions: Role Prompting → authority/tone, Style Prompting → explicit style, Emotion Prompting → engagement.
- **Implementation Lessons:** Changing exemplar order alone swings results 30-40%. Technique effectiveness is model-dependent. Many techniques compose (CoT + Role), but some are mutually exclusive (zero-shot vs. few-shot) — grammar layer needs a compatibility matrix.
- **Priority for MVP vs. Later:** **MVP** — foundational taxonomy.

### DSPy's Prompt Compilation Pipeline
- **Source:** https://github.com/stanfordnlp/dspy | https://dspy.ai/
- **Relevance to textchisel:** Closest existing architecture to a grammar layer — compiles high-level signatures into concrete prompts.
- **Technical Enablers:** Signatures as declarative specs. Modules as technique selectors (Predict, ChainOfThought, ReAct). Adapters (ChatAdapter, JSONAdapter) handle signature→prompt translation. Three learnable parameters: LM weights, instructions, demonstrations.
- **Implementation Lessons:** DSPy separates information flow (program structure) from parameters (prompts/weights) — maintain this separation in textchisel.
- **Priority for MVP vs. Later:** **MVP** — template architecture pattern.

### Quality Dimension → Prompt Modification Mapping
- **Source:** Han et al., 2025 (Springer) | promptengineering.org | latitude.so
- **Relevance to textchisel:** Concrete mapping from abstract qualities to implementable modifications.
- **Technical Enablers:**

| Dimension | Prompt Modifications | API Parameters |
|-----------|---------------------|----------------|
| Scientific Rigor (0→1) | "Cite sources," hedging language, confidence levels, Role="researcher" | temperature: 0.2→0.1 |
| Formality (0→1) | "Use formal register, avoid contractions," formal few-shot examples | top_p: 0.8→0.3 |
| Urgency (0→1) | "Be direct and concise," imperative mood, remove hedging | shorter max_tokens |
| Creativity (0→1) | "Explore unconventional angles," metaphors | temperature: 0.3→0.9, top_p: 0.4→0.95 |
| Detail/Depth (0→1) | "Provide comprehensive analysis," "Address edge cases" | max_tokens: increase |

- **Implementation Lessons:** Quality dimensions are NOT independent — increasing scientific rigor naturally reduces creativity. Grammar layer needs constraint awareness. Prompt text AND API parameters (temperature, top_p, max_tokens) should be co-optimized.
- **Priority for MVP vs. Later:** **MVP** — rule-based mappings.

### Modular Prompt Architecture
- **Source:** https://github.com/danielrosehill/System-Prompt-Factory | https://blog.promptlayer.com/prompt-routers-and-modular-prompt-architecture-8691d7a57aee/
- **Relevance to textchisel:** Compose prompts from independent, swappable modules — direct grammar layer pattern.
- **Technical Enablers:** HTML-like tags: `<role>`, `<requirements>`, `<output_format>`, `<constraints>`. 6-component model: Task, Guidance, Context, Intent, Role, Parameters. Separate Persona, Core Logic, Output Format into sections. Regex-delimited sections for programmatic manipulation.
- **Implementation Lessons:** Start with 4-5 slots maximum. Module boundaries must be clean. Use Jinja2 conditionals: `{% if scientific_rigor > 0.5 %}Include citations{% endif %}`.
- **Priority for MVP vs. Later:** **MVP** — core template system.

### Rhetorical Structure Theory in NLP
- **Source:** https://github.com/EducationalTestingService/rstfinder | Various RST parsing tools
- **Relevance to textchisel:** Maps discourse structure to quality dimensions: EVIDENCE/JUSTIFICATION → scientific rigor; CONCESSION → nuance; ELABORATION → depth.
- **Technical Enablers:** 24-76 rhetorical relations. RSTFinder: fast shift-reduce parser. Nucleus/satellite structure: adjust ratios for different quality settings.
- **Implementation Lessons:** Most useful for evaluating output quality post-generation rather than directly generating prompts. Translate RST concepts into natural language instructions.
- **Priority for MVP vs. Later:** **Phase 3** — advanced evaluation.

### LangChain Prompt Composition
- **Source:** https://python.langchain.com/docs/concepts/prompt_templates/
- **Relevance to textchisel:** Battle-tested composition patterns for the grammar layer implementation.
- **Technical Enablers:** `PipelinePromptTemplate` composes sub-templates — each independently rendered and injected. `ChatPromptTemplate` models multi-message structure. Jinja2 templates with conditionals for slider-conditional logic. `MessagesPlaceholder` for dynamic insertion.
- **Implementation Lessons:** PipelinePromptTemplate is the key pattern but has limited adoption. LangChain's string-centric approach becomes clunky at scale — consider Mirascope for structured-data prompts.
- **Priority for MVP vs. Later:** **MVP** — composition engine.

## AREA 7: Latency Optimization for Interactive LLM Applications

### Streaming LLM Responses via SSE
- **Source:** https://dev.to/pockit_tools/the-complete-guide-to-streaming-llm-responses-in-web-applications-from-sse-to-real-time-ui-3534
- **Relevance to textchisel:** First tokens appear in ~200-500ms instead of waiting 3-8s for complete response.
- **Technical Enablers:** SSE with `Content-Type: text/event-stream`. Express + OpenAI: `stream: true` + `for await (const chunk of stream)`. React progressive rendering per chunk.
- **Implementation Lessons:** "Latency Theater" — perceived latency drops dramatically. For textchisel: stream generation AND begin scoring partial outputs before generation completes.
- **Priority for MVP vs. Later:** **MVP** — essential for perceived performance.

### Parallel LLM API Calls
- **Source:** LLMCompiler (https://github.com/SqueezeAILab/LLMCompiler, ICML 2024) | asyncio patterns
- **Relevance to textchisel:** Score 5 evaluation dimensions at 1.5s each → 1.5s total instead of 7.5s.
- **Technical Enablers:** `asyncio.gather()` for concurrent calls. `AsyncOpenAI` / `AsyncAnthropic` clients. textchisel evaluation dimensions are independent → all can run in parallel. 4 sequential 300ms calls = 1.2s → parallel = ~300ms.
- **Implementation Lessons:** textchisel's dimensions are independent — trivially parallelizable.
- **Priority for MVP vs. Later:** **MVP** — critical for <8s loop.

### Semantic Caching (GPTCache)
- **Source:** https://github.com/zilliztech/GPTCache | https://arxiv.org/abs/2411.05276
- **Relevance to textchisel:** Slider adjustments often produce semantically similar prompts. Cache hits return instantly.
- **Technical Enablers:** Embedding-based similarity search (FAISS, Milvus). Configurable similarity threshold (~0.90). Hit rates of **61-68%** in production. Cache lookup: ~0.2s. Supports SQLite, Redis backends.
- **Implementation Lessons:** Use threshold ~0.90 for quality. Adjacent slider positions (±1-2) will likely cache-hit. Consider GenerativeCache (9× faster than GPTCache).
- **Priority for MVP vs. Later:** **Phase 2** — performance optimization.

### Incremental Prompt Editing & Predicted Outputs
- **Source:** https://developers.openai.com/api/docs/guides/latency-optimization/
- **Relevance to textchisel:** Maximize KV cache reuse by putting slider-variable content at END of prompt.
- **Technical Enablers:** **Predicted Outputs**: provide prediction when most output is known. **Shared prefix maximization**: static instructions first, dynamic parameters last → enables provider-side prompt caching. **Combine steps**: merge generation + evaluation into single LLM call.
- **Implementation Lessons:** 50% fewer output tokens ≈ 50% less latency. Structure prompts with static prefix + dynamic suffix.
- **Priority for MVP vs. Later:** **MVP** — prompt structure optimization.

### Optimistic UI Updates (React 19)
- **Source:** https://react.dev/reference/react/useOptimistic | https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates
- **Relevance to textchisel:** Show predicted evaluation scores instantly, replace with actual when available.
- **Technical Enablers:** `useOptimistic(currentState, reducerFn)` updates UI inside `startTransition`. Auto-reverts when async completes. TanStack Query: `onMutate` → snapshot → optimistic update → rollback on error.
- **Implementation Lessons:** Interpolate predicted scores from nearby cached results. User perceives <100ms response. Always implement rollback for prediction misses.
- **Priority for MVP vs. Later:** **MVP** — perceived performance.

### Speculative Precomputation
- **Source:** SpeQL (https://arxiv.org/html/2503.00714v1) | Google speculative decoding research
- **Relevance to textchisel:** Pre-compute adjacent slider positions in background while user examines current state.
- **Technical Enablers:** SpeQL predicts query structure and precomputes superset results. Speculative decoding: small draft model generates candidates, large model verifies in parallel (2-3× speedup). EAGLE-3 eliminates separate draft model.
- **Implementation Lessons:** Pre-warm likely slider positions. Even partial precomputation (shared prefix) reduces latency.
- **Priority for MVP vs. Later:** **Phase 2** — advanced optimization.

**Target <8s pipeline:**

## AREA 9: Dimension Orthogonality and Coupling Analysis

### Jacobian Analysis for Abstract Quality Spaces
- **Source:** https://ml4eng.github.io/camera_readys/47.pdf | Cambridge Design Science (Jacobian/Hessian uncertainty)
- **Relevance to textchisel:** Compute J_{ij} = Δquality_i / Δslider_j to map dimension coupling.
- **Technical Enablers:** Numerically estimate Jacobian by perturbing each slider and measuring quality changes. PyTorch autodiff if using neural surrogate. **Hessian cross-terms** ∂²quality/∂slider_a∂slider_b reveal interaction effects — large cross-terms = coupled sliders.
- **Implementation Lessons:** Build surrogate neural net predicting quality from sliders, compute Jacobian for continuous sensitivity map. Validate against Sobol indices.
- **Priority for MVP vs. Later:** **Phase 2** — coupling detection.

### PCA-Based Objective Reduction (Deb & Saxena)
- **Source:** https://www.egr.msu.edu/~kdeb/papers/k2010008.pdf
- **Relevance to textchisel:** Detect redundant quality dimensions using PCA on collected evaluation scores.
- **Technical Enablers:** L-PCA and NL-MVU-PCA algorithms. Variance threshold (θ = 0.682) for significant PCs. Identifies "identically correlated sets" of objectives. Biplot: angle between vectors shows correlation.
- **Implementation Lessons:** If two dimensions always load on the same PC, alert users: "Dimensions X and Y appear redundant (r=0.95)." Variance explained tells effective dimensionality.
- **Priority for MVP vs. Later:** **Phase 2** — user guidance.

### SALib — Sobol Sensitivity Analysis
- **Source:** https://github.com/SALib/SALib | https://salib.readthedocs.io/
- **Relevance to textchisel:** Gold-standard for measuring which sliders affect which quality dimensions and how they interact.
- **Technical Enablers:** **S1** (first-order): direct effect of slider i. **S2** (second-order): interaction between sliders i and j — **directly measures coupling**. **ST** (total-order): total including all interactions. If ST >> S1, significant interactions exist. **Morris method** for cheap screening. Workflow: `saltelli.sample(problem, N)` → evaluate → `sobol.analyze(problem, Y)`.
- **Implementation Lessons:** For 5 sliders: N×12 evaluations needed. With N=100 → 1200 LLM evals. Use Morris first (cheap screening) then Sobol for detailed analysis. S2 indices directly measure coupling between slider pairs.
- **Priority for MVP vs. Later:** **Phase 2** — sensitivity analysis.

### Concept Sliders Disentanglement Technique
- **Source:** https://sliders.baulab.info/ | https://arxiv.org/abs/2311.12092
- **Relevance to textchisel:** The preservation set approach to ensuring slider independence.
- **Technical Enablers:** To edit attribute A without affecting attribute B, specify B as a preservation concept. Optimization forces the slider to work identically across all preservation concepts. Loss: maximize P(c+, p | X) while minimizing P(c-, p | X) for all preservation concepts p.
- **Implementation Lessons:** Over 50 sliders compose without degradation in high-dimensional space. Low-rank constraint is critical for localized edits.
- **Priority for MVP vs. Later:** **Phase 2** — disentanglement.

### Objective Dimensionality Reduction (Brockhoff & Zitzler)
- **Source:** https://sop.tik.ee.ethz.ch/publicationListFiles/bz2007d.pdf
- **Relevance to textchisel:** Detect when a quality dimension is redundant (removing it doesn't change which prompts are "better").
- **Technical Enablers:** MINIMUM OBJECTIVE SUBSET (MOSS): find smallest subset preserving dominance structure. Greedy algorithm for approximate solution. Tests on Pareto set approximations.
- **Implementation Lessons:** Implement greedy objective reduction. Alert users when dimensions can be removed without information loss.
- **Priority for MVP vs. Later:** **Phase 3** — advanced dimension management.
